# Phase 14 — Deep Interview Pack

# Question

What did Phase 14 add to Smart Cricket?

## Short Answer

It converted `spoken_feedback` text into audio-ready voice output and produced frontend-ready audio metadata.

## Deep Technical Explanation

Phase 14 consumes the spoken feedback text generated by the feedback engine and exposed by the API. It validates the text, generates a playable audio artifact, and returns a frontend audio-ready response containing both text and audio metadata.

## Engineering Reasoning

Voice output should be the last layer because it depends on meaningful prediction, scoring, and feedback.

## Why This Decision Was Taken

The roadmap places voice after API integration so the system can deliver complete coaching responses first.

## Tradeoffs / Risks / Limitations

The local environment could not produce natural speech audio through macOS `say`, so the implementation uses a playable WAV fallback and keeps the provider boundary ready for production TTS.

## Important Engineering Insight

Audio artifacts must be validated. A command can appear to succeed while producing an unusable file.

# Question

Why does Phase 14 consume `spoken_feedback` instead of creating new feedback?

## Short Answer

Because feedback logic belongs to Phase 11. Voice should only speak the existing feedback.

## Deep Technical Explanation

The `spoken_feedback` string is already designed to be concise and TTS-friendly. Phase 14 converts that string into audio output. It does not re-score, reinterpret, or rewrite coaching advice.

## Engineering Reasoning

This prevents mismatch between visible feedback and spoken feedback.

## Why This Decision Was Taken

The roadmap says voice depends on meaningful feedback and should come after feedback generation.

## Tradeoffs / Risks / Limitations

If the spoken feedback text is weak, voice output will also be weak.

## Important Engineering Insight

Output layers should preserve upstream meaning, not invent new decisions.

# Question

Why keep TTS behind a separate service boundary?

## Short Answer

So the project can swap providers later without rewriting feedback or API logic.

## Deep Technical Explanation

The `tts_service.py` module owns spoken text validation, audio generation, provider selection, and audio metadata. Other modules consume its output through a stable response shape.

## Engineering Reasoning

TTS providers vary by platform, cost, latency, quality, and deployment constraints.

## Why This Decision Was Taken

The roadmap says not to hardcode one provider too early.

## Tradeoffs / Risks / Limitations

The v1 local fallback is not a final production voice experience.

## Important Engineering Insight

Provider isolation protects the architecture from vendor and environment changes.

# Question

How does Phase 14 validate audio output?

## Short Answer

It checks that audio is generated, playable, non-empty, and matches the spoken feedback text.

## Deep Technical Explanation

The validator loads the Phase 13 sample response, extracts `spoken_feedback`, generates an audio artifact, writes a frontend audio-ready response, and stores health metadata.

## Engineering Reasoning

Voice output should not be marked complete just because a file path exists.

## Why This Decision Was Taken

Integration validation found that macOS `say` produced header-only files in this environment, so real payload validation was necessary.

## Tradeoffs / Risks / Limitations

The validator proves local audio readiness, not production TTS quality.

## Important Engineering Insight

Artifact validation should inspect usability, not only existence.

# Question

What is the frontend audio-ready response?

## Short Answer

It is a JSON response containing spoken feedback text plus audio availability, path, format, bytes, and debug metadata.

## Deep Technical Explanation

The response allows a frontend to show the text feedback and know whether an audio artifact is available for playback.

## Engineering Reasoning

Frontends need both visible text and audio metadata. Voice should not hide the underlying feedback.

## Why This Decision Was Taken

The roadmap requires frontend audio-ready output.

## Tradeoffs / Risks / Limitations

Local file paths are development artifacts. A deployed version should serve URLs or streams.

## Important Engineering Insight

Audio output needs an integration contract, not just a generated file.

# Question

How does Phase 14 complete the roadmap?

## Short Answer

It adds the final voice/audio-ready output layer after prediction, scoring, feedback, inference, and API.

## Deep Technical Explanation

The system now covers the core project arc: data processing, temporal modeling, segmentation, technique scoring, coaching feedback, inference, API integration, and voice-ready output.

## Engineering Reasoning

This turns the project from a model-training exercise into a complete AI engineering system.

## Why This Decision Was Taken

The roadmap defines voice as the final core system phase.

## Tradeoffs / Risks / Limitations

Production hardening remains: raw-video support, deployment, frontend UI, natural TTS provider, and coach-reviewed calibration.

## Important Engineering Insight

Roadmap completion does not mean production perfection; it means the full architecture exists end to end.
