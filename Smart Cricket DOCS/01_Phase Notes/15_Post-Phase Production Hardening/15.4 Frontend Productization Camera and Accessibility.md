# 15.4 Frontend Productization Camera and Accessibility

## Problem

The website needed to feel like a real cricket-analysis workspace, not a demo wrapped around an API. It also needed to avoid misleading users about camera state, storage state, feedback eligibility, and model certainty.

## Concept

The frontend is built as a focused practice-review tool:

- clear product identity;
- demo mode labelled as local;
- camera framing guidance;
- countdown and recording timer;
- preview before submission;
- honest analysis progress;
- results with uncertainty, quality notes, probabilities, timing, audio state, and storage state;
- feedback controls gated by capabilities and evidence retention;
- history with trusted/local/demo labels.

## Accessibility Decisions

The UI uses semantic sections, labelled form fields, `aria-live` status messages, visible focus states, native controls where possible, and reduced-motion CSS. The design avoids fake skeleton or pose overlays because the backend does not return real pose landmarks to the browser yet.

## Tests

Frontend coverage includes camera MIME behavior, unsupported recorder fallback, retention capability disabled state, feedback reset, feedback eligibility copy, history trust filtering, accessibility checks, and a Playwright UI contract flow with mocked backend routes.

## Interview Implications

Short answer: the frontend now tells the truth about what is saved, local, uncertain, or unavailable.

Deep answer: Product polish is not only visual. In this project, polish means the interface respects trust boundaries: demo mode is local, unsaved history is labelled, and feedback cannot claim model-review eligibility unless evidence was retained before analysis.
