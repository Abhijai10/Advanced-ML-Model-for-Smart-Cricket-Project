# 15.5 Testing Docker CI and Deployment Readiness

## Problem

Production readiness needs evidence, not confidence. The project required stronger checks across backend, frontend, ML utilities, Docker, and CI.

## Concept

The verification strategy separates:

- local unit and component tests;
- browser UI contract tests;
- container smoke tests;
- real-video E2E harness;
- external deployment gates.

## Implementation

CI covers Python, frontend lint/build/tests, Playwright, and container smoke. The API Docker image runs as a non-root user, installs production dependencies, includes the MediaPipe pose asset, and exposes health/readiness probes.

Important files:

- `.github/workflows/ci.yml`
- `Dockerfile.api`
- `backend/api/tests/`
- `frontend/src/components/*.test.tsx`
- `frontend/e2e/app.spec.ts`
- `ml/src/inference/tests/test_true_raw_video_e2e.py`

## Tests

The latest local pass recorded:

```text
python3 -m pytest -q
```

The skipped test is the honest Phase 12 real-video harness. It requires `ml/data/e2e/raw_batting_fixture.mp4` with legal project/test provenance.

## Failure Modes

Docker and Supabase local verification can be blocked by host tooling or missing credentials. In that case, the project keeps static/mocked/integration-script coverage and marks live verification as `Blocked External`.

## Interview Implications

Short answer: CI proves the code-feasible paths, but it does not prove real-world ML validity.

Deep answer: The test matrix is intentionally honest. Mocked browser tests prove UI contracts; they do not prove MediaPipe accuracy. Container smoke proves deployability of the image; it does not prove production TLS or Supabase RLS in a live project.
