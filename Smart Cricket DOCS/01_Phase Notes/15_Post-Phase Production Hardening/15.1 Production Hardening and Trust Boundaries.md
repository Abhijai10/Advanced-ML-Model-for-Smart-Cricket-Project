# 15.1 Production Hardening and Trust Boundaries

## Problem

The original Smart Cricket prototype could demonstrate the pipeline, but production readiness requires stronger trust boundaries. A public coaching product must distinguish uploaded user bytes from stored demo data, trusted server history from local UI state, user feedback from ground truth, and private retained evidence from public assets.

## Concept

The hardening pass treats every boundary as explicit:

- browser input is untrusted;
- server inference output is trusted only after backend validation;
- analysis history is trusted only when created by the backend;
- user feedback is evidence, not a label;
- model-improvement data requires consent, retained evidence, and human review;
- external gates remain blocked until real credentials, users, videos, and coaches exist.

## Implementation

The core boundary is:

```text
User video
→ upload validation
→ raw-video inference
→ server-owned analysis metadata
→ optional consented evidence retention
→ feedback bound to verified analysis
→ human review
→ adjudicated export only
```

Important files:

- `backend/api/routes.py`
- `backend/api/services.py`
- `backend/api/persistence.py`
- `backend/api/evidence.py`
- `frontend/src/App.tsx`
- `docs/MASTER_PRODUCTION_READINESS_CHECKLIST.md`

## Tradeoffs

The project is stricter about claims now. Some features are marked partial even when the code path exists, because live Supabase, real devices, larger data, and coach validation are external evidence gates.

## Tests

Regression coverage includes filename-inference rejection, forged feedback rejection, trusted history persistence metadata, feedback eligibility gates, evidence deletion, and frontend history trust labels.

## Interview Implications

Short answer: Smart Cricket moved from prototype behavior to explicit production trust boundaries.

Deep answer: The most important production decision is that the browser cannot declare what is trusted. The server owns analysis history, the reviewer workflow owns training eligibility, and the model card owns the limits of ML claims.
