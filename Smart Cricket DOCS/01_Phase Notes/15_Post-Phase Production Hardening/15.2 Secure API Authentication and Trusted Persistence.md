# 15.2 Secure API Authentication and Trusted Persistence

## Problem

If the frontend can write analysis rows directly, a user can forge shot labels, confidence, model metadata, or history. Production history must be created by the backend after real inference.

## Concept

Authentication identifies the user. Persistence proves that an analysis row came from the backend. Row-level security limits what browser clients can read or delete, while service-role credentials stay server-side.

## Implementation

The API supports:

- optional or required authentication by environment;
- HS256 JWT verification for legacy Supabase projects;
- RS256 and ES256 JWKS verification for modern asymmetric keys;
- issuer, audience, expiry, `nbf`, signature, and subject validation;
- backend-only Supabase writes;
- server-returned `analysis_session_id`;
- frontend history reconciliation from server rows.

Important files:

- `backend/api/services.py`
- `backend/api/persistence.py`
- `backend/api/tests/test_auth.py`
- `supabase/migrations/20260804080002_secure_trusted_analysis_and_feedback.sql`
- `frontend/src/App.tsx`

## Failure Modes

- Missing auth in strict mode returns 401.
- JWKS outage returns controlled 503.
- Persistence failure does not fail analysis, but the frontend marks history as unsaved.
- A fabricated or cross-user analysis ID cannot be used for model feedback.

## Tests

Auth tests cover valid and invalid HS256, RS256, ES256, malformed tokens, expired tokens, future `nbf`, wrong issuer/audience, unknown `kid`, JWKS cache refresh, invalid JWKS, HTTP failures, and route-level outage behavior.

## Interview Implications

Short answer: the frontend can display results, but the backend is the source of truth for saved history.

Deep answer: This prevents forged ML evidence. A trusted history row contains server-created provenance: model version, feature contract hash, checkpoint hash, clip hash, and request metadata.
