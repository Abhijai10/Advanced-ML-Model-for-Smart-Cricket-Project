# 15.3 Human in the Loop Feedback and Evidence Retention

## Problem

User feedback is useful for improving Smart Cricket, but it is not ground truth. A player may mislabel a shot, misunderstand the coaching tip, or report feedback without enough video evidence for a reviewer to verify the claim.

The production hardening pass therefore separates three ideas:

- product feedback: usability, bug, and feature reports;
- analysis feedback: a user's judgement about one verified analysis;
- training candidates: only consented, reviewable, retained evidence after human adjudication.

## Implementation

General app feedback now goes to `public.product_feedback` through `POST /product-feedback`. It no longer enters `analysis_feedback`, so it cannot accidentally appear in model-training exports.

Analysis feedback still uses `POST /feedback`, but the backend derives trusted fields from the server-created `analysis_session_id`. The browser cannot submit trusted prediction, clip hash, model version, provenance, review status, or dataset eligibility.

Model-improvement participation is disabled unless `SMART_CRICKET_ALLOW_MODEL_IMPROVEMENT_PARTICIPATION=true`. The backend exposes this through `GET /capabilities`, and the frontend disables evidence-retention and feedback-consent controls when participation is off.

## Evidence Lifecycle

Evidence deletion is provider-aware. The system uses `evidence_metadata.storage_provider` from the original record instead of the current runtime provider setting. This matters because a clip retained in local development, Supabase Storage, or a future provider must be deleted from the place where it was actually stored.

Consent withdrawal now:

1. verifies the analysis belongs to the authenticated user;
2. disables training eligibility immediately;
3. attempts physical evidence deletion;
4. marks successful deletion as `deleted`;
5. marks failed deletion as `deletion_pending` for retry.

The cleanup command is:

```bash
python scripts/cleanup_evidence.py
python scripts/cleanup_evidence.py --execute
```

The first command is a dry run. The execute mode deletes expired or pending evidence and marks the database rows so they remain excluded from review and training.

## Tradeoffs

This pass implements the code contract and local/mock verification. Live Supabase Storage verification remains external because it requires a real project, bucket policy, and credentials. That is acceptable for a restricted internal beta, but not enough for public production.

## Interview Notes

The key answer is: Smart Cricket does not train directly from user feedback. Feedback becomes a candidate only when there is explicit consent, retained evidence, complete provenance, and human review. Product feedback and ML feedback are intentionally separate because mixing them would contaminate the training pipeline and create privacy risk.
